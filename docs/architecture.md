# 架构与固定来源

`YunXia` 开发协议管理工具、数据契约、适配器和项目采用 Skill；`YunXia-Agreements` 维护协议正文、设计、审阅、registry、状态和发布事实。协议仓库是这些事实的唯一维护位置，工具仓库只保存来源锁和适配支持。

## 本地工作区

```text
YunXia/                         # 工具仓库，独立 .git
├── sources.lock.json
├── tooling/
├── skills/yunxia/
├── docs/
└── repositories/              # 父仓整体忽略
    └── YunXia-Agreements/      # 协议仓库，独立 .git 和 origin
        ├── repository.json
        ├── toolchain.lock.json
        ├── agreements/<id>/
        ├── registry/<id>/
        ├── provenance/
        └── docs/
```

子仓是普通独立 Git 仓库，不使用 submodule，父仓索引不得出现其文件或 gitlink。`repositories/` 是实际工作区，工具源码检查、打包和清理不能递归收集或删除它。克隆工具仓库不会自动得到子仓，需要显式获取来源。首次获取建立远端默认分支的工作树，供维护使用；已有目录获取时不切换分支，构建始终读取来源锁中的确切提交。执行协议命令前须核对 Git 顶层目录就是目标路径，避免空目录向上发现父仓。

## 三类输入

工具源码、协议仓库和采用项目各有独立根路径。协议维护命令只读取或修改指定协议仓库；构建将工具和固定协议快照组合；项目采用只操作目标项目。

`sources.lock.json` 保存协议来源的稳定 ID、仓库地址、完整目录提交及允许纳入的协议 ID。本地默认路径是 `repositories/<来源ID>/`，个人绝对路径不写入锁文件。相同协议 ID 不能由两个选定来源提供，摘要相同也不能自动合并发布或撤回事实。

锁定目录提交与 registry 中的 `source.commit` 不同：前者包含本次消费的登记和维护状态；后者固定已审阅正文及材料。正式版本目录应包含已核验的发布回执；历史草案保持原身份，不需要为了构建而正式发布。普通构建不跟随 `main`、`latest` 或未提交工作树，也不自动更新来源锁。缺对象、来源身份冲突或摘要不符时明确失败。

协议仓库的 `toolchain.lock.json` 固定维护工具来源和完整工具提交，CI 只调用它进行协议校验，不要求先构建包含该协议的新 Skill。工具基础测试生成独立协议夹具，锁定真实协议快照的集成验收另行执行，避免双仓循环依赖。

## 历史迁移

协议仓库的 `main` 从独立起点维护协议资料，`history/pre-split` 固定拆分前工具仓库提交及其完整历史，两者不合并。保留旧 Git 对象是原引用的取材依赖，不是另外生成工作区备份。默认 main 的提交和 PR 不混入旧工具开发历史。

三份 imported-draft 的 registry 原字节迁移，协议 ID、版本、正文摘要、来源提交和取材路径均不变。迁移清单记录原仓库、截止提交、固定历史引用、登记摘要及载荷来源；清单不复制正文，不补造审阅、候选或发布。

协议校验同时覆盖新 main 和清单固定的旧历史根，防止拆仓绕过版本不可改绑、登记不可删除以及已发布事实不可抹去的约束。迁移清单及历史根也不能删改。旧工具仓库在截止提交之后移除协议目录，不属于协议仓库的历史删除。

原仓完整 SHA 的链接、三字段采用引用和登记来源保持有效；指向原仓 `main` 当前路径的导航改为协议仓库入口。删除原 main 文件不会为外部浮动 raw URL 创建重定向，不用正文镜像伪装第二份维护来源。普通完整克隆协议仓库应能取得全部必要历史，浅克隆或缺少历史引用须先补齐固定对象。

## Skill 分发

适配登记在工具仓库，逐项绑定协议 ID、版本、正文 SHA-256、适配器和输出名；它不改变协议发布状态。构建分别记录工具输入、来源锁定提交和包内文件摘要，保留所收录协议的固定历史版本。安装包携带引擎、目录快照及原字节资产，离开两仓且无 Git、无网络仍可采用。

项目状态格式保持 3，采用身份仍是 `agreement_id/version/sha256`。仓库位置、迁移信息和构建提交属于目录及分发来源，不注入项目采用身份。来源更新、工具升级和推荐变化不会自动改写项目已有绑定；离线包只能报告构建时已收录的维护状态。

协议发布、来源更新、适配登记和项目采用分别完成并核验。两个仓库各自提交推送，通过确切提交衔接，不假设跨 Git 和远端服务存在单次原子事务。
